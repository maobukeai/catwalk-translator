# OCR 模型 A/B：2026-09-28

范围：现有 5 张真实截图；Small、Tiny、Medium 使用同一 RapidOCR/ONNX Runtime CPU 流程、同一参数（含 `unclip_ratio=1.0`）、同一台机器。每图预热后取 3 次中最快耗时。模型文件放在系统临时目录，未加入应用设置或替换已安装模型。

四张有完整逐行标注的截图合计 703 字符：Small 24 错，Tiny 27 错，Medium 15 错。字符错误含空格、标点和漏字；它不是通用准确率，样本也不足以证明对任意界面有效。Blender 图未做逐行标注，不能计入汇总。非文字区域与合法文字框局部重叠，因此目前不能给出可靠的误识别图标率。

另用项目本身的 Rust 回归测试复核密码标题裁剪：Small 的产品 OCR 路径为 8/67 错，Tiny 为 4/67 错；Small 原始 Rust ONNX 路径为 16/67 错。同一个 Small 模型在独立 RapidOCR 流程是 0/67 错。这是项目处理流程差异的证据，不能把错字全部归因于模型本身。两条路径耗时不可直接比较，因为预处理、后处理和融合策略不同。

结论：暂不将 Medium 纳入正式模型列表或设为默认。先对比两条实现的输入缩放、检测阈值/框扩张、文字裁剪与旋转、识别输入尺寸、字典解码，以及后续行融合；修复流程差异后重新跑相同截图，再决定是否提供 Medium 作为非实时高精度选项。界面字号、背景遮挡及翻译覆盖位置须单独做视觉回归，OCR 模型 A/B 无法验证这些问题。

复现模型级实验：`uv run --no-project --python 3.12 --with rapidocr --with onnxruntime python app_v2/scripts/ocr_model_ab.py <包含 small/tiny/medium 子目录的临时模型目录>`。脚本只读取模型和截图，不修改产品配置。

## 新增密集中文正文样本

用户后续提供的 807×171 中文正文截图已纳入 `ocr_real_cases.json`，标注五条物理行、225 个字符（含链接附近括号）。旧产品流程在旧版 223 字标注上切成 22 框、27 处差异；独立 RapidOCR Small/Tiny 均约 7/223，WinRT 为 40/223。数字的标注版本不同，不把它们当作严格同分母模型排名。

排查确认：产品的 `should_refine_dense_toolbar` 将任意含四个以上汉字的低行高宽框判成工具栏，对已经正确识别的正文再次按墨迹空白切分、重识别，造成“了→7”等错误。收紧 Small 的工具栏判定后，产品输出变为五条完整行，按修订后的 225 字标注为 7/225；该样本预热后最快耗时由约 711 ms 降至约 121 ms。链接符号附近仍有误识，不能据此宣称整页或其它字体已准确。气泡、Blender、终端和密码弹窗回归仍须同时运行。

同一正文保护扩展到 Tiny 后，该图从 21 框、24/225 差异变为 5 框、8/225 差异，预热最快约 43 ms；聊天气泡保持 0/52。Small 在其它实图上：密码弹窗 0/228、密码标题 0/67、气泡 0/52、终端 25/356，Blender 已有关键字检查通过。Tiny 的旧质量门槛仍有未通过项：终端约 25/356 且标签关闭图标误检，密码标题 4/67，Blender 缺 `UV编辑` 和 `F5切英文`。这些要作为后续独立问题处理，不能用正文样本的进步掩盖。

可单图复核独立模型：在上面的命令后加 `--image dense_chinese_prose_source.png --tiers small tiny --raw`。产品路径使用 `CATWALK_REPRO_IMAGE=<该 fixture 路径> CATWALK_OCR_VERSION=v6 cargo test --test ocr_repro dump_ocr_pipeline_for_image -- --nocapture --ignored`；前者测模型及 RapidOCR 流程，后者测产品实际 Rust 流程。
